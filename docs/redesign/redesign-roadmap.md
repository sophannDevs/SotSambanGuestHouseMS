## 0. Naming collision, resolved up front

This redesign task defines its own **12 phases** (§42 of the task brief: Audit → Design Foundation → App Shell → Shared Components → Dashboard → Reservations → Front Desk → Property Operations → Guest and Finance → Management → Mobile/PWA Polish → Final QA). The project's **own** `docs/product-requirements.md` independently defines a **different** 12 phases for building the product itself (§16, referenced by `source-brief.md` B44: Planning → Local setup → Auth → Property/Settings → Rooms/Rates → Guests/Reservations → Front Desk → Payments/Documents → Operations → Expenses/Reports → PWA/Mobile → Testing). They share the number 12 by coincidence and are otherwise unrelated. Every phase reference below is labelled **Redesign Phase N** or **Build Phase N** explicitly — never a bare "Phase N" — to keep the two straight.

**A documentation gap found while cross-referencing them**: `product-requirements.md` is itself unfinished. It stops mid-§9 at FR-222 (Check-Out, §9.15) with a literal `<!-- CONTINUE -->` placeholder in the file — sections 9.16 onward (Payments through Languages), §10 (page inventory) through §18 (glossary), **including §16's own Development-phases table, do not exist yet.** This roadmap therefore cross-references `source-brief.md` B44 (which is complete) plus the `Ph` column values actually present on FR-001–FR-222 for build-phase mapping, rather than a §16 that isn't there. ## 1. Guiding principles (carried from Phase 1's other documents)

1. **Refine, don't replace** — `current-ui-audit.md` §0/§15, `skill-usage-report.md`'s adoption of `impeccable`'s principle. Every redesign phase below is a refactor of what exists, not a rewrite.
2. **Redesign and first-real-wiring are the same pass, for most domains** — because the frontend is currently 0% wired to a backend that is often already real (`current-ui-audit.md` Appendix A). Each phase below states which pages get wired to live data and which get an honest placeholder, based on that appendix — not on assumption.
3. **No placeholder theatre.** Where a backend domain is `NOT STARTED` (rate, availability, refund, notification, file upload, audit log, search, dev-reset), the redesigned screen must say so clearly (per the brief's own empty-state contract: what's missing, why, what to do next) rather than keep a convincing-looking mock number.
4. **Fix the bug in the same pass as the page it's on.** Two confirmed functional bugs exist today (non-functional search on `invoices` and `expenses`, `current-ui-audit.md` §9) — fixed when those pages are redesigned, not filed separately.
5. **No Docker, deployment, CI/CD, or production infrastructure at any point** — carried through every phase below without exception, per the brief's explicit instruction and `product-requirements.md` §7's hard prohibitions.

## 2. Standing work method for every phase (brief §44, adopted verbatim)

Before implementing any phase: read the relevant skill guidance already catalogued in `skill-usage-report.md` (mainly the `shadcn` skill's rule files), re-inspect the specific files that phase touches (code moves during a 12-phase project — re-verify, don't trust this audit's snapshot forever), explain the concrete problem, list files to modify, describe the approach, implement, run `npm run lint` and `npm run type-check` (both are real scripts in `guesthouse-web/package.json`), run any existing tests, start the app locally (`mvnw spring-boot:run` + `npm run dev`, per `docs/local-setup.md`), verify desktop and mobile manually, record findings, fix regressions, update the affected doc in `docs/redesign/`. No phase is reported done on "it compiles" alone.

### 3.1 Implementation notes (recorded after doing the work)

**Status: done and verified** (Playwright screenshot pass against the running dev server at desktop 1440px and mobile 390px on `/dashboard`, `/reservations`, `/rooms`, `/check-in`, `/login` — all render pixel-consistent with the pre-existing design; the one console error found traces to the pre-existing hardcoded-relative-fetch bug on the login page already documented in `current-ui-audit.md`, not to anything in this phase).

**A real, recurring problem worth knowing before Redesign Phase 3+ installs more components**: the installed `shadcn@4.16.0` CLI generates component source targeting Tailwind **v4**'s engine, even when it correctly detects this project as v3 (`tailwindVersion: "v3"`). Concretely, every `npx shadcn add <component>` going forward may include:

1. `data-open:`/`data-closed:`/`data-checked:`/etc. shorthand variants, which only exist via v4's `@custom-variant` CSS (which itself only ships through the v4-only `shadcn/tailwind.css` import this phase had to remove entirely, since it uses `@theme inline`/`@utility`/`--value()` syntax v3's PostCSS pipeline cannot parse). **Already fixed centrally** — `tailwind.config.ts` now registers a small `addVariant()` plugin mapping each shorthand to the real Radix `data-state`/`data-orientation` attribute it should match. No action needed on future `add` calls for this specific issue.
2. `var(--radius-md)`-style references to v4 auto-generated theme variables. **Already fixed centrally** — `--radius-sm/-md/-lg/-xl` are now defined directly in `globals.css` alongside `--radius`.
3. The `gap-(--foo)`/`p-(--foo)` **parenthesis arbitrary-value syntax** (v4-only; v3 only supports the bracket form `gap-[var(--foo)]`) paired with a locally-set variable via v4's `--spacing()` theme function (e.g. `[--card-spacing:--spacing(4)]`). This is **not fixed centrally** — it can't be; v3's parser doesn't support the alternate bracket dialect at all, so there's no plugin-level fix. `components/ui/card.tsx` needed a direct hand-edit (replaced the dynamic-spacing-variable indirection with plain `gap-4`/`py-4` + a `group-data-[size=sm]/card:` variant for the compact-size case) because without it the whole component would have rendered with **no padding or gap at all**. **Action for every future `add`**: run `grep -oE "\-\-spacing\(|\-\(--" <newfile>.tsx` on each newly-added file before trusting it; if it matches, read the file and translate the dynamic-variable pattern to plain utility classes the same way, following `design-system.md`'s already-decided fixed padding scale (§4) rather than reinventing a per-component spacing token.

One cosmetic-only, deliberately-not-fixed gap: `Tooltip`'s zoom animation uses `origin-(--radix-tooltip-content-transform-origin)` (same parenthesis syntax) for its transform-origin; under v3 this silently generates no CSS, so the tooltip's scale-in animation defaults to a center-origin instead of anchor-relative. Functionally harmless (Radix still positions and shows/hides the tooltip correctly) — noted here rather than patched, since it's a one-line animation nicety, not a layout break.

**Also fixed in this phase, not originally scoped but discovered while verifying**: `npx shadcn init` added `@base-ui/react` (the CLI's "nova" preset defaulted to Base UI primitives on a bare `--preset nova`, not Radix — required an explicit `--base radix` flag, undocumented in the `shadcn` skill's own `cli.md` but present in the installed CLI's `--help`) and `tw-animate-css` (v4-only, same incompatibility as above) as dependencies; both were removed and replaced with `radix-ui` (correct primitives, per `conventions.md`) and `tailwindcss-animate` (the v3-native equivalent, registered as a Tailwind plugin). No ESLint config existed anywhere in the project before this phase (`next lint` had never successfully run) — added a standard `eslint.config.mjs` (flat config, `next/core-web-vitals` + `next/typescript`) since the standing work method requires a passing lint step; running it surfaced ~40 pre-existing lint errors (unused imports, unused state setters) across pages this phase didn't touch — these are real and consistent with `current-ui-audit.md`'s findings, left for each page's own redesign phase to fix rather than mass-fixed here.

### 6.1 Implementation notes (recorded after doing the work)

**Status: done and verified.** Removed both literal build-status blocks (`backendActive`/`nextPhase`) entirely rather than replacing them with a new section — the acceptance criteria call for removing fabricated content, not inventing a new feature in its place. All four stat cards now compute from real endpoints with zero placeholders needed: `GET /rooms` (occupancy % and a housekeeping clean/dirty/cleaning breakdown, both derived from real per-room `operationalStatus`/`housekeepingStatus` fields — the same "compute from real granular data" approach the mobile room-status legend already used before this phase, just extended to numbers instead of a dot legend), `GET /front-desk/arrivals` + `GET /front-desk/in-house` (today's expected arrivals, already-checked-in-today, and today's check-outs), and `GET /payments` (today's revenue and transaction count). Every card is gated behind the same permission the backend's `@PreAuthorize` actually checks (`room:view`/`reservation:view`/`payment:view`, read via `hasPermission()` from `lib/auth-store.ts`) and simply omitted — not shown as an error — for a role that lacks it, mirroring the sidebar's existing nav-filtering convention rather than inventing a new access-denied pattern.

**A real, cross-cutting bug found and fixed, not specific to this page**: this is the first page in the whole app to make an authenticated `apiFetch` call (per Phase 4's own note, `apiFetch` was previously unused everywhere), and every one of its four queries failed with a CORS error on first verification. Root cause: `SecurityConfig.java` never called `.cors(...)`, so Spring Security's filter chain — which runs *before* `WebConfig`'s `WebMvcConfigurer.addCorsMappings` ever gets a chance to act — applied `anyRequest().authenticated()` to the browser's CORS preflight `OPTIONS` request too. Preflight requests carry no `Authorization` header, so they were rejected before any `Access-Control-Allow-Origin` header was ever added, and the browser reported a CORS failure rather than a 401. This is why `/auth/login` (in the `permitAll` list, so its own `OPTIONS` preflight also matches `permitAll`) worked while every other endpoint didn't. Fixed by moving the CORS policy into a `CorsConfigurationSource` bean wired via `.cors(cors -> cors.configurationSource(...))` in `SecurityConfig.java`, and removing the now-redundant, non-functional mapping from `WebConfig.java` (kept as a single source of truth rather than two independently-drifting configs). This was blocking **every future redesign phase**, not just the dashboard — Phase 6 onward would have hit the identical failure the moment any page tried its first real fetch.

**A second real gap found**: `/front-desk/arrivals` and `/front-desk/departures` are not date-filtered server-side (confirmed in `ReservationService.getReservations` — no date parameter exists at all); `arrivals` returns every `CONFIRMED`/`PENDING` reservation ever, and `departures` returns exactly the same list as `in-house` (`CHECKED_IN`, unfiltered). Worked around by filtering client-side against "today" in the property timezone — added `isTodayInPropertyZone()` to `lib/dates.ts` (extending Phase 4's date helpers, not duplicating them) and comparing `arrivalDate`/`departureDate` against it. This is a legitimate computation over real data, not a fabrication, but the underlying backend limitation is worth flagging to the project owner as a Build Phase 7 follow-up (proper date-scoped arrivals/departures queries) rather than something the frontend should keep working around indefinitely.

**One status-badge gap fixed in passing**: the room legend's bucketing surfaced `derivedStatus: "OCCUPIED_DIRTY"` (a real value `RoomService.computeDerivedDisplayStatus` produces, per `business-rules.md` §9.6/FR-075) that had no entry in `status-badge.tsx`'s `STATUS_TONE` map nor `messages/en.json`'s `enum.status` — added both (`danger` tone, "OCCUPIED (DIRTY)"/Khmer equivalent), the same completeness gap class Phase 4 was built to close.

**Documentation drift found while verifying, worth flagging to the project owner**: `docs/local-setup.md` §14's demo credentials table (`owner@guesthouse.local` / `Demo@1234`, 7 seeded roles) does not match reality — the actual seed data (`V003__seed_roles_and_permissions.sql`) creates exactly 3 users at `@sotsamban.local` with password `password123` (owner, manager, receptionist only; no housekeeping/maintenance/readonly accounts exist to test those permission tiers against). Not fixed here since `docs/local-setup.md` is outside `docs/redesign/`'s scope, but noted since it cost real verification time and will cost more for the next person following that guide.

**Verified**: `npm run type-check` and `npm run lint` both pass with no new errors introduced (the dashboard file has zero lint findings of its own). Live end-to-end verification via a headless-Chromium pass logged in as `owner@sotsamban.local`: zero console errors after the CORS fix, no hardcoded build-status text anywhere in the rendered output, and the four numbers cross-check against each other (7 total rooms = 3 available + 2 occupied + 1 cleaning + 1 maintenance; "1 Stays" expected arrival matches the mobile "Bookings: 1" tile) confirming they share one real data source rather than being independently faked. Both desktop (1440px) and mobile (390px) layouts render correctly.

**Two corrections to this section's own original wording, found by reading the live code instead of assuming the plan was still accurate**:
1. `SearchInput`/`FilterBar` do not exist anywhere in `components/shared/` and were never built in an earlier phase — the actual established search pattern (used correctly by `invoices/page.tsx` since an earlier phase) is `DataTableToolbar` + `DataTable`/`ResponsiveDataList`. Rather than introduce two new component names that would duplicate `DataTableToolbar`'s exact job, guests/payments/expenses were migrated onto the existing `DataTableToolbar`/`DataTable` pair instead — consistent with Redesign Phase 8's precedent of not inventing parallel components when an existing one already covers the need.
2. `invoices/page.tsx`'s search was already fully functional (a real `React.useMemo` filter wired to both `DataTable` and `ResponsiveDataList`) — the actual broken search box was on **`expenses`** only: a `search` input existed and updated state, but the table body mapped directly over the unfiltered `expenses` array, so typing had zero visible effect. Fixed as part of the same migration, not a separate ticket.

**A real, pre-existing backend bug found and fixed, not just documented — same bug class as Redesign Phase 8's `housekeeping:edit`/`maintenance:edit`**: `PaymentController.recordPayment` checked `hasAuthority('payment:process')` and `ExpenseController.createExpense` checked `hasAuthority('expense:submit')` — neither permission key exists anywhere in the seed catalogue (`V003__seed_roles_and_permissions.sql` seeds `payment:view/create/void/adjust` and `expense:view/create/edit/approve/delete`, with `payment:create` described as "Process payment" and `expense:create` described as "Create expense" — clear evidence these were the intended keys, likely a copy-paste naming slip when the controllers were written). Since neither `:process` nor `:submit` is ever granted to any role — including OWNER, who is granted every row that actually exists in `permissions` — `POST /payments` and `POST /expenses` would 403 for every real user, unconditionally, exactly like the Phase 8 finding. Fixed both `@PreAuthorize` annotations to reference the correct, already-seeded, already-correctly-described keys (`payment:create`, `expense:create`). Confirmed live: a real payment and a real expense were both recorded successfully as OWNER after the fix.

**A second real backend bug, found only by looking at what the payments/invoices pages would actually render, not just their DTOs**: `PaymentService.mapToPaymentDto` and `PaymentService.getInvoices` hardcoded the literal strings `"RSV"` and `"Guest"` for every payment's reservation number and every payment's/invoice's guest name, instead of joining to the real `Reservation`/`Guest` data the service already had access to. Left as-is, the redesigned payments and invoices tables would have shown the identical fake placeholder text on every single row — a regression more visible and more damaging to user trust than the mocked screens they were replacing. Fixed `PaymentService` to batch-load the referenced reservations (`reservationRepository.findAllById`, one query per list call rather than N+1) and derive the real `reservationNumber` and guest display name from `Reservation.getMainGuest()`; `recordPayment` reuses the reservation it already loaded rather than querying again. Confirmed live: the payments table shows real reservation numbers and real guest names (e.g. "RSV-2026-000007" / "John Smith"), not "RSV" / "Guest".

**Guests** (`guests/page.tsx`, `guests/[id]/page.tsx`) — resolved the two-independent-mock-dataset drift by wiring both pages to the same `["guests"]` query (`GET /guests`), which structurally prevents the drift from recurring (there is only one data source now, not two hand-authored shapes). There is no `GET /guests/{id}` endpoint, so the detail page derives the guest from the already-fetched list, the same "no per-item GET" constraint Redesign Phases 7–8 already hit for reservations and rooms. The old mock's fabricated `totalStays`/`totalBookings`/`totalSpending`/`latestCheckIn` fields (present on one mock, absent or differently-named on the other) are now computed for real by cross-referencing the already-fetched `["reservations"]` list against `reservation.mainGuest.id` — there is no dedicated guest-stats endpoint, so this cross-reference (same pattern as the room board's guest-name lookup in Phase 8) is the only honest way to show these numbers. The old "View Booking History" button was a bare toast leading nowhere; since the reservations are already fetched for the stats above, the guest detail page now renders the real booking history inline (each row linking to the real `/reservations/{id}`) instead of a dead-end button. Built a real "New Guest" dialog (`components/guests/new-guest-dialog.tsx`) calling `POST /guests`, gated on `guest:edit` (the key the backend actually enforces — `guest:create` exists in the permission catalogue but nothing checks it, the same "seeded but dead" pattern documented for several permissions this phase). Guest edit/merge/blacklist/anonymize have no backend at all (confirmed: `GuestController` only has the two endpoints) and were never present in the old mock UI either, so no new placeholder needed — nothing was removed or hidden that used to work.

**Payments** (`payments/page.tsx`) — wired to `GET /payments`; built a real "Record Payment" dialog (`components/payments/record-payment-dialog.tsx`) with a reservation search-and-select (mirroring `reservations/new`'s guest-picker pattern) that defaults the amount to the reservation's real `balanceDue`, calling `POST /payments`. The dialog deliberately excludes "Refund" from the payment-kind selector even though the backend accepts any string there: `recordPayment` always **adds** the submitted amount to `paidAmount` regardless of `paymentKind`, so selecting "Refund" would increase the guest's balance instead of decreasing it — exposing it as a selectable option would have been building a fake capability that actively does the wrong arithmetic, worse than not having the option at all. Real refunds have no backend support (confirmed: no void/refund code path anywhere), so this is deliberately left as a gap, not silently worked around. The old mock's receipt-download button is now a disabled button with an explanatory tooltip — there is no receipt endpoint and `PaymentDto` doesn't even carry a receipt number, so there was no real data to back a working button.

**Expenses** (`expenses/page.tsx`) — wired to `GET /expenses`, with the broken search fixed as described above. Built a real "Record Expense" dialog (`components/expenses/new-expense-dialog.tsx`) calling `POST /expenses`. `ExpenseService.createExpense` auto-approves every expense on creation (`// Auto approve in local mode`), so there is no pending-approval workflow to build UI for today — the real `PUT /expenses/{id}/approve` endpoint is still wired as a conditional "Approve" action (visible only when `approvalStatus !== "APPROVED"`) so any legacy or seeded non-approved expense can still be approved through the UI, rather than assuming the auto-approve behavior is the only path that will ever exist.

**Invoices** (`invoices/page.tsx`) — already used the target `DataTable`/`DataTableToolbar`/`ResponsiveDataList` pattern and had working search; only the mock data was replaced with `GET /invoices`. `InvoiceDto` carries `reservationId` but not a human-readable reservation number, so it's cross-referenced against the `["reservations"]` list rather than shown as a raw UUID (same pattern as the payments/guests pages this phase). "New Invoice" and the per-row "Preview" action are both disabled with explanatory tooltips rather than a clickable toast — there is no invoice-issuance code path and no PDF generation anywhere in the backend (confirmed again this phase: the one invoice type constant is `STANDARD`/`TAX_INVOICE`, but nothing ever creates a new `Invoice` row at runtime).

**Verification performed**: `npx tsc --noEmit` clean; `next build` succeeds with zero errors or warnings. Backend recompiled clean after the permission and `PaymentService` fixes. Started the real backend and frontend and drove the live UI with Playwright: created a real guest, searched the guest directory, viewed a guest's detail page with real cross-referenced booking history, recorded a real payment against a real reservation, viewed the invoices list, and recorded a real expense — every mutating call (`POST /guests`, `POST /payments`, `POST /expenses`) returned a real success response and the affected data was visibly updated afterward. One real bug was caught only by this live run and fixed before calling the phase done: the payment-method/kind `Select` dropdowns and the expense-category `Select` dropdown initially rendered raw, unresolved translation-key strings (e.g. `payments.recordDialog.methods.CASH`) instead of their labels, because the dialogs looked up shared `methods`/`kinds`/`categories` keys relative to their own nested namespace (`payments.recordDialog.*`) instead of the parent namespace where those keys actually live (`payments.*`) — a mismatch invisible to `tsc`/`next build` since it's a runtime string, not a type error, but visible immediately as garbled UI text and a spike in next-intl's missing-message console errors during the live pass. Fixed by having each dialog pull those specific shared keys from a separately-scoped `useTranslations` call pointed at the correct parent namespace. The verification script and its temporary `playwright` package were removed afterward rather than shipped.
